# Authentication risk engine

## Flow and threat model

Fortify remains responsible for password verification, passkey verification, TOTP and recovery codes, login sessions, and logout. The login route has two independent request limits: identity plus client IP (5 per minute by default) and client IP (30 per minute). These limits remain active in monitor mode. A separate listener records actual password failures across IPs, failures from one IP, and distinct identities attempted from one IP. Short-lived counters are never calculated from sampled audit rows.

After Fortify validates a password, `AssessPasswordLoginRisk` scores the request before an authenticated session is created. The score and decision stay on the server. Monitor mode records sampled risk events and permits Fortify to continue. Enforcement requires both `risk_mode=enforce` and `risk_step_up=true`. Medium risk uses Fortify's existing TOTP or single-use recovery code for enrolled accounts. Fortify's challenge session is extended with a five minute risk expiry and cleared after success. Without an enrolled factor, medium risk temporarily denies password sign-in. High risk denies password sign-in for the current identity and source for ten minutes. Medium and high cooldowns are source-scoped and configurable in `config/authentication-risk.php`. A verified Fortify password reset can recover the account: the reset token creates a ten minute, session-bound, single-use marker for the next validated password login. This fallback relies on the user's email account and does not bypass enrolled MFA. Errors do not reveal account existence.

The account-wide failure signal is deliberately worth only 15 points. Combined with an unknown device it remains below the default medium threshold, so remote failures alone cannot deny the owner. Source failures and spraying can raise the score for the source making the request. This system addresses password guessing, credential stuffing, and spraying, but cannot reliably identify a distributed botnet using one attempt per IP.

## Signals and scoring

Weights are in `config/authentication-risk.php`. Defaults are unknown device 10, account failures at threshold 15, source failures (10 in the window) 30, five distinct targeted accounts from one source 25, source volume at the configured IP threshold 10, and changed user-agent on a recognized device 10. Total score is capped at 100. Low is below `medium_risk_threshold` (30); medium is below `high_risk_threshold` (70); high is at or above it. Browser consistency is disabled by default. A browser version change alone never restricts access. Implement `App\Security\Signals\RiskSignal` and list classes in `authentication-risk.signals` to add local signals; their combined contribution is capped at 20 points. Review new signals for privacy and denial-of-service behavior.

The failure window defaults to 10 minutes. `RiskCounterService` uses Laravel RateLimiter for expiring counters and atomic cache increments, and `Cache::add` for distinct-target markers. Identity and source cache keys are HMACed with `APP_KEY`; never rotate that key solely to reset counters. The database cache driver is the default and requires the cache table and a shared database across workers. Redis can be selected with Laravel's normal `CACHE_STORE` configuration. Do not use a per-worker array cache in production. The source IP comes from Laravel's trusted client-IP resolution.

## Trusted devices

After a completed password, TOTP, or passkey login, a 256-bit random browser token is issued in a Secure, HttpOnly, SameSite=Lax cookie. Only its SHA-256 hash is stored in `trusted_devices`. The cookie is independent of the Laravel session. Devices are never registered during an unfinished TOTP challenge or before mandatory MFA enrollment. A recognized, unexpired and unrevoked device is a lower-risk signal, never an authenticator. The Security Settings page lists name and seen dates, and can revoke one or all devices. Revocation removes trust for subsequent sign-ins; existing sessions remain active. Database sessions can be revoked separately through the existing administrative emergency action. Expired records and records revoked over 30 days ago are deleted by the daily `audit:prune` schedule.

The displayed name is the first 255 characters of the HTTP user-agent. It is untrusted, spoofable browser metadata and is retained only until expiry or revocation pruning. Browser consistency comparison is optional and uses that stored value; no canvas, font, hardware, or other high-entropy fingerprint is collected. A stolen device cookie can make an attacker appear recognized, but does not replace a password, passkey, or mandatory MFA. Use HTTPS and `SESSION_SECURE_COOKIE=true` in production; the trusted-device cookie is always Secure. Set short device expiry where shared computers are common.

## Fortify and configuration

Passkey login and confirmation keep Fortify's existing endpoint limiter (10 per minute) and WebAuthn verification. Passkeys provide a phishing-resistant factor and are not interrupted by the password risk challenge. The two-factor endpoint keeps its existing 5 per minute limit. Frozen-account and emergency-lockdown checks continue through the existing Login event listener and session middleware. The risk engine cannot override either restriction.

The Owner edits risk settings under Authentication & Security. Sensitive changes require password confirmation and are written by `SettingsService`, which validates ranges and records before/after values in the configuration audit log. Defaults: monitor mode, step-up off, trusted devices on, 30 day expiry, 10 minute window, browser signal off, 30 source requests per minute, 10 account failures per window, and medium/high thresholds of 30/70. The identity/IP limiter remains configurable with its existing 5 per minute default. Baseline limits cannot be turned off from this page. High-risk decisions are evaluated automatically in Fortify's pre-session pipeline so enforcement can happen before login completes. Their audit records are written immediately; a throttled high-severity email notification is queued to the Owner when security notifications are enabled and a real mail transport is configured. Keep a Laravel queue worker running for delivery.

Security audit events include sampled risk decisions, challenge required/succeeded/failed, temporary restriction, and device registration/revocation. Properties are allowlisted score, signal names, and risk level only; tokens, passwords, recovery codes, and attempted identities are omitted. In `/admin/users`, the Security activity link opens that user's security events in the existing investigation detail view. `/admin/activity-logs` can filter all security events and medium/high risk levels. Audit access remains protected by `audit.view`; exports keep the same field allowlist. The existing audit retention policy deletes security events after `AUDIT_SECURITY_RETENTION_DAYS` (730 by default). Risk decisions use live counters, regardless of audit sampling.

## Deployment and operations

Run `php artisan migrate --force` before serving new code. Keep `APP_KEY` stable. Configure `TRUSTED_PROXIES` as comma-separated IPs or CIDR ranges of actual reverse proxies in Docker, Coolify, or a VPS; leave it unset when directly exposed. Never use `*` or trust arbitrary forwarding headers. Verify `request()->ip()` reflects the real client through the configured proxy. Put a coarse request limit at the reverse proxy or WAF as another layer. Run `php artisan schedule:run` every minute so the existing daily audit and device pruning runs.

To investigate unexpected restrictions, inspect the `security` activity events and confirm source IP, proxy trust, cache connectivity, configured thresholds, and whether an enrolled factor exists. To validate changes run `php artisan test tests/Feature/Auth/AuthenticationRiskTest.php`, the existing authentication and configuration suites, `npm run check`, and `npm run build`.

Known limitations: source IP and user-agent are weak, shared-network signals can increase risk scores, email alert delivery depends on the mail and queue configuration, passkey sign-in is not separately risk restricted, and device revocation does not revoke a live session. Treat monitor-only observations from real traffic as the input to enabling enforcement.
