# Activity logging

Fuyutsuki stores audit records with `spatie/laravel-activitylog` in `activity_log`. The published migrations use integer polymorphic IDs, matching `users`, `groups`, and `permissions`. Four categories are used: `users`, `security`, `authorization`, and `system`. Rows record event, subject, actor when known, timestamp, and approved JSON properties. Indexes cover category, event, actor, subject, and time filters.

`User`, `Group`, and `Permission` use the package's `LogsActivity` trait. Their `getActivitylogOptions()` methods explicitly list approved fields and omit empty changes. Only user name, email, verification time, and frozen time, plus group and permission name, slug, and description, are recorded. Passwords, hashes, tokens, passkeys, two-factor secrets, recovery codes, sessions, and request bodies must never be added to a log. For a new model, add the trait and an explicit field allowlist; review every field before deployment.

Fortify authentication events are handled by `AuditAuthentication`. Failed logins are limited to five records per IP per minute and do not include the attempted identity. Security records contain only a validated client IP, when present. Password changes in the settings controller are recorded without values. Group assignments and permission syncs are logged inside their existing database transactions with before and after IDs. For other business operations, call `activity('system')->performedOn($model)->event('operation.name')->withProperties($approvedFields)->log('operation.name')` inside the operation's transaction. Never pass entire models or request arrays as properties. System jobs without an authenticated user have no causer.

Authentication risk counters use expiring Laravel cache keys independently of activity rows. Risk decisions are sampled per source, account, and level; challenge, restriction, and trusted-device lifecycle events are security activities with allowlisted properties. See [authentication risk engine](authentication-risk-engine.md). `audit:prune` also removes expired trusted devices and devices revoked over 30 days ago.

The read-only `/admin/activity-logs` page requires both `admin.access` and `audit.view`. CSV export also requires `audit.export`, and is capped at 10,000 records per request. The `audit.manage-retention` permission is reserved for future operational controls; no UI or mutation route uses it. The RBAC seeder grants the Owner all catalog permissions, including audit view and export. Run `php artisan permissions:sync` and the RBAC seeder or apply equivalent controlled permission provisioning after deployment. Existing assignments should be reviewed before rerunning a seeder that syncs group permissions.

Set `AUDIT_RETENTION_DAYS` (default 365) and `AUDIT_SECURITY_RETENTION_DAYS` (default 730). `audit:prune` deletes expired nonsecurity rows and applies the longer period to security rows. Laravel schedules it daily in `routes/console.php`. In Docker/Coolify, configure a scheduler worker or cron that runs `php artisan schedule:run` every minute with the same application environment and database access. Run `php artisan migrate --force` during deployment before serving requests; never reset the database. Check migration status and scheduler logs after deployment.

Audit rows are editable by database operators, so this table is not tamper-proof. Use a restricted application database role, limit direct database access, back up the table, and consider external append-only archival if stronger evidence preservation is required. Retention and indexes control growth, but monitor table size and query latency. If logs are missing, check `ACTIVITY_LOGGER_ENABLED`, migration status, scheduler output, and that the event path actually fires. Run `php artisan test tests/Feature/ActivityAuditTest.php` to verify the core behavior.
